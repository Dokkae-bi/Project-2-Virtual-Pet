# ECGR 4101/5101 — Virtual Pet (Project 2)

Tamagotchi-style virtual pet running on a **NUCLEO-L496ZG-P** with an
**X-NUCLEO-GFX01M2** (2.2" QVGA ILI9341 SPI TFT + joystick) display expansion board.

> **Status:** **the pet runs.** `main.c` starts it, the joystick drives the menu,
> and the sprite, both meters and the menu are drawn on the panel. Shaking the
> MPU-6050 (I2C) plays with the pet, and a potentiometer (ADC) sets how much it
> eats. 347 host checks pass with no board attached. What's left is the hardware
> verification — **see
> [`TODO.md`](TODO.md)**.

---

## 1. The pet

**Name:** Bloop *(working name — see `docs/pet-design.md`)*
**Concept:** A small cyan-teal slime with no limbs, so everything it does is a
shape. It breathes by squashing and stretching, jumps by stretching upward, and
collapses into a flat puddle when it starves. Its mood shows through **three
channels at once** — body colour, silhouette and face — so you can tell what it
needs at a glance rather than having to read the meters.

**Artwork:** master PNGs live in `docs/artwork/`. Converted RGB565 assets live in
`sprites/` and are generated by `tools/png_to_rgb565.py`, not hand-edited — the
seven slime states, plus a berry and a heart icon for the meters. There is also a
rendered `docs/artwork/ui-mockup.png` of the whole screen, generated from the
layout constants so it cannot drift from the code. Design rationale is in
[`docs/pet-design.md`](docs/pet-design.md).

### Statistics and consequences

Both statistics are clamped to a closed range, so no amount of neglect or
over-feeding can push them outside it.

| Stat | Range | Changes over time | Changed by |
|---|---|---|---|
| Food | 0–100 | **−1 every 1.2 s** | feeding (+12 per portion), play (−9) |
| Happiness | 0–100 | **−1 every 2.0 s** | play (+22), clean (+14), feeding (+4) |

| Outcome | Trigger | Screen / animation | Restart procedure |
|---|---|---|---|
| Death | food reaches 0 — **90 s** of total neglect from the initial 75 | `slime_dead`, collapse animation, loops | joystick CENTER |
| Runaway | happiness reaches 0 — reached by *feeding enough to stay alive* while happiness drains | `slime_runaway`, drifting animation, loops | joystick CENTER |

Both are terminal: the pet stops accepting actions and its statistics freeze until
it is restarted. The two endings are reached by different behaviour — pure neglect
starves it, attentive-but-unfulfilling care makes it run away.

All of these are `#define`s at the top of `Core/Inc/pet_core.h`, so they are
tuning knobs rather than magic numbers.

### Actions

The three required interactions are offered on an in-game menu, opened with the
joystick. Selecting one plays its animation and applies its effect immediately.

| Action | Physical input | State effect | Animation |
|---|---|---|---|
| **Feed** (required) | menu item; the **potentiometer** selects the portion (1–5) | food +12 × portion, happiness +4 | `slime_eating` plus a squashing transform |
| **Play** | menu item, or **shake the MPU-6050** | happiness +22, food −9 | jump transform of the mood sprite |
| **Clean** | menu item | happiness +14 | wobble transform of the mood sprite |
| Idle | — | passive decay | 4-frame breathing loop; the mood picks the sprite |

Only Feed affects the pet differently depending on a peripheral: the analog input
chooses how much it eats, and the menu displays the current portion next to the
Feed row.

## 2. Hardware

### Boards

| Item | Notes |
|---|---|
| NUCLEO-L496ZG-P | STM32L496ZGT6P, Cortex-M4F, 1 MB flash, 320 KB RAM |
| X-NUCLEO-GFX01M2 | 2.2" 240×320 QVGA TFT (ILI9341), SPI NOR flash, 5-way joystick |

### ⚠️ Assembly prerequisites and hazards

1. **Morpho headers must be soldered** on the NUCLEO-L496ZG-P. They are *not*
   populated from the factory, and the GFX01M2 cannot be attached without them.
   **This is the current blocker on all hardware work.**
2. **Orientation is destructive if wrong.** The GFX01M2 must be aligned with the
   *top* of the morpho headers exactly as shown in the course handout. Plugging it
   any other way may damage the board.
3. **Disconnect USB power before attaching or changing any display connection.**

### Pin map (from `Drivers/BSP/GFX01M2/gfx01m2_conf.h`)

| Signal | Pin | Notes |
|---|---|---|
| LCD SPI (SCK/MISO/MOSI) | `PA5` / `PA6` / `PA7` | `SPI1`, 1.775 MHz |
| LCD chip select | `PA9` | ⚠️ see conflict note below |
| LCD data/command | `PB10` | high = data, low = command |
| LCD hardware reset | `PA1` | active low |
| Joystick LEFT | `PB6` | active low, internal pull-up |
| Joystick CENTER | `PC7` | active low, internal pull-up |
| Joystick DOWN | `PB4` | active low, internal pull-up |
| Joystick RIGHT | `PB0` | active low, internal pull-up |
| Joystick UP | `PC0` | active low, internal pull-up |
| User button B1 | `PC13` | configured for a rising-edge interrupt, **but the EXTI IRQ is never enabled** — poll it |
| Potentiometer wiper | `PA3` | `ADC1_IN8`, analog (`GPIO_MODE_ANALOG_ADC_CONTROL`) |
| I2C1 SCL (MPU-6050) | `PB8` | AF4, open drain, 100 kHz |
| I2C1 SDA (MPU-6050) | `PB9` | AF4, open drain |
| LD2 (green) | `PB7` | **on = shake sensor answering**, off = missing or unplugged |

### ⚠️ `PA9` is claimed twice — do not initialise USB Host

`PA9` is both the **LCD chip select** and `USB_OTG_FS_VBUS` in the `.ioc`. The demo
avoids this only because it never calls `MX_USB_HOST_Init()`. The project still
compiles `USB_HOST/` and `main.h` still defines `USB_VBUS_Pin`, so **calling
`MX_USB_HOST_Init()` will reconfigure `PA9` and blank the display.** Leave USB host
uninitialised. Use `LPUART1` (`PG7`/`PG8`, already wired to the ST-LINK virtual COM
port) for any serial logging instead.

### Additional peripherals (required: ≥1 analog + ≥1 I2C/UART/SPI device)

Selected in `docs/pet-design.md`.

| Role | Device | Status |
|---|---|---|
| Analog input | **Potentiometer** (10 kΩ linear) | **in the code, not yet verified on hardware.** `ADC1_IN8` on `PA3`; selects the feeding portion 1–5 |
| I2C device | **GY-521 / MPU-6050** accelerometer | **in the code, not yet verified on hardware.** `I2C1` **remapped to `PB8`/`PB9`**, address `0x68`, 100 kHz |
| Optional output | PWM buzzer | not started; tone per mood, chirp per action |

The I2C remap is not optional: the CubeMX default `I2C1` pins are `PB6`/`PB7`,
and **`PB6` is the joystick LEFT input** while `PB7` drives `LD2`. Enabling I2C1
on its defaults silently breaks the joystick.

#### MPU-6050 shake sensor

| GY-521 pin | Connect to |
|---|---|
| VCC | 3V3 |
| GND | GND |
| SCL | `PB8` |
| SDA | `PB9` |
| AD0, INT, XDA, XCL | leave unconnected (AD0 is pulled low on the board → address `0x68`) |

Check UM2179 (the Nucleo-144 user manual) for which header pins carry `PB8`/`PB9`
before wiring — the GFX01M2 may cover the Zio connector, in which case use the
morpho pins. **Unplug USB before wiring.**

How it works:

- The accelerometer is read at **±2 g, 100 Hz** (44 Hz on-chip low-pass filter),
  polled from the main loop every 10 ms — no `HAL_Delay`, no interrupt.
- **A shake is 3 jolts within 1 s.** A jolt is |a| ≥ **1.8 g**; another can only
  be counted once |a| has dropped back to ≤ **1.3 g**, so one long push is one
  jolt. After a shake, the detector ignores the sensor for **1.5 s**, so non-stop
  shaking can't spam Play. All of these are `#define`s at the top of
  `Core/Inc/pet_shake.h`.
- A shake triggers **Play** through `pet_ctl_action()`, exactly like the menu —
  only on the pet screen, never behind an open menu. A dead or runaway pet
  refuses it.
- **Missing or unplugged sensor:** the pet keeps running without it, `LD2` turns
  off, and the sensor is looked for again once a second, so plugging it back in
  recovers without a reset. Every failure also frees the bus (nine SCL pulses and
  a STOP) and restarts I2C1, because a wire glitch can otherwise leave it stuck
  "busy" until the board is reset. Once a second it also checks the sensor hasn't
  browned out and gone back to sleep, which would read as zeros without failing.
- `WHO_AM_I` must read `0x68` (genuine) or `0x70`/`0x72` (clones commonly fitted
  to GY-521 boards with the same accelerometer registers).

#### Potentiometer (feeding portion)

| Pot pin | Connect to |
|---|---|
| one end | 3V3 |
| other end | GND |
| wiper (middle) | `PA3` |

`PA3` should be **A0** on the Nucleo-144 Zio connector. Confirm it in UM2179
before wiring, and **never connect the pot to 5 V**: the ADC pin's limit is the
3.3 V supply. Swap the two end wires if you want the knob to run the other way.

How it works:

- ADC1 reads `PA3` every **20 ms**: 12-bit, a single software-started
  conversion of about 7 µs. No `HAL_Delay`, no DMA, no interrupt.
- The range is split into five equal bands, giving **portion 1–5**. A running
  average takes out noise, and the reading has to go **60 counts (~1.5%)** past a
  band edge before the portion changes, so a knob resting on an edge can't make
  the menu flicker. The tuning is `#define`d in `Core/Inc/pet_pot.h`.
- The portion is shown beside the Feed row and is exactly what Feed uses:
  food +12 × portion.
- **Unavailable input:** a failed conversion keeps the last portion, so Feed
  still works. A disconnected wiper leaves `PA3` floating and reads as a random
  portion — if the number wanders on its own, check the wiper wire.

## 3. Controls

| Input | Action |
|---|---|
| Joystick UP / DOWN | move the menu selection (wraps at both ends) |
| Joystick CENTER | open the menu, confirm the highlighted action, or restart a finished pet |
| Joystick LEFT / RIGHT | reserved — no action yet |
| User button B1 (`PC13`) | close the menu without acting (`PET_INPUT_BACK`) — **not wired up yet, see TODO.md** |
| Potentiometer → ADC | selects the feeding portion, 1–5, shown beside the Feed row |
| Shake the MPU-6050 (I2C1) | **Play** — on the pet screen only, at most once per 1.5 s |

Input handling lives in `Core/Src/pet_ui.c` and is driven by logical events
(`pet_input_t`), so the whole control scheme is tested on a PC without the board.

### Layering

The five `pet_*` modules contain **no HAL calls at all**. They take a millisecond
timestamp as an argument and return plain data, which is what lets the whole
behavioural side be tested on a laptop:

```
pet_core    what is true about the pet
pet_anim    which animation should be playing
pet_render  how a frame of that animation is scaled
pet_view    which sprite to use, and the finished frame
pet_ui      what the user is looking at and what an input event means
pet_hud     where everything goes on the 240x320 panel, and the meter maths
pet_ctl     applies an action to the pet and starts its animation
pet_screen  draws it all - the only one that talks to the display
```

Only `pet_screen` and `main.c` touch the hardware. Everything above them is
tested on a PC.

### Graphics interface (`ili9341.h`)

Supplied by the course: `ILI9341_Init`, `FillScreen`, `DrawPixel`, `FillRect`,
`DrawHLine`, `DrawVLine`, `DrawLine`, `DrawRect`, `DrawChar`, `DrawString`.

**Added by the team:** `ILI9341_DrawBitmap` — an opaque RGB565 sprite blit. It had
to go in `ili9341.c` because `LCD_SetAddressWindow()` is `static` there. It
converts RGB565 to the panel's byte order itself, so the asset files stay readable
and are never hand-swapped.

## 5. Build and flash

### Prerequisites

- VS Code with **STM32CubeIDE for VS Code** (`stmicroelectronics.stm32-vscode-extension`)
- Bundle Manager toolchain installed (ARM GCC 14.3.1, CMake, Ninja, ST-LINK GDB server)
- **Do not** install Cortex-Debug or the C/C++ extension pack — they conflict with the
  bundled clangd and debug adapter

### Build

Open the folder in VS Code and either:

- `Cmd+Shift+P` → **`CMake: Build`**, or
- press **`F5`** — the launch config has `preBuild`, so it builds then flashes

From a terminal:

```bash
cmake -S . -B build/Debug -G Ninja -DCMAKE_BUILD_TYPE=Debug \
      -DCMAKE_TOOLCHAIN_FILE=cmake/gcc-arm-none-eabi.cmake
cmake --build build/Debug
```

The terminal configure must find the **ST bundle's** `arm-none-eabi-gcc` first on
`PATH`. A Homebrew `arm-none-eabi-gcc` has no C library headers and fails with
`stdint.h: No such file or directory`. On macOS:

```bash
export PATH="$HOME/Library/Application Support/stm32cube/bundles/gnu-tools-for-stm32/14.3.1+st.2/bin:$PATH"
```

> ⚠️ **I2C1 and ADC1 are enabled by hand.** `HAL_I2C_MODULE_ENABLED` and
> `HAL_ADC_MODULE_ENABLED` were uncommented in `Core/Inc/stm32l4xx_hal_conf.h`;
> `MX_I2C1_Init`/`MX_ADC1_Init` live in `USER CODE` blocks of `main.c` and the MSP
> inits in `USER CODE 1` of `stm32l4xx_hal_msp.c`. The ST ADC driver files
> (`stm32l4xx_hal_adc*.c/.h`, `stm32l4xx_ll_adc.h`) were copied unmodified from
> STM32Cube_FW_L4 V1.18.2 and are built from the top-level `CMakeLists.txt`.
> The `.ioc` knows about none of this. Before regenerating from CubeMX, either
> add I2C1 (`PB8`/`PB9`) and ADC1 (`PA3`, IN8) there **and delete the hand-written
> `MX_*_Init` and `HAL_*_MspInit` copies** (or the link fails with duplicates),
> or re-apply the two `hal_conf.h` lines afterwards.

### Flash

**Run and Debug** (`Cmd+Shift+D`) → **`STM32Cube: Launch ST-Link GDB Server`** → `F5`.
`Shift+F5` stops the session; the image stays in flash. Press the board's black
**RESET** to re-run standalone.

CLI alternative:

```bash
STM32_Programmer_CLI -c port=SWD mode=normal \
  -w build/Debug/Lab1_NUCLEO_L496.elf -v -rst
```

### Smoke test

Build and flash the **unmodified** starter before adding any pet code. Verify the
display clears to several colours, draws text and rectangles, and responds to the
joystick. If the screen stays blank, check power, wiring, board revision and SPI
pins **before** debugging application code.

## 6. Performance constraints (measured, not guessed)

SPI1 runs at **1.775 MHz** (`PCLK2 56.8 MHz ÷ 32`) ≈ **221,875 bytes/s**:

| Operation | Transfer time |
|---|---|
| Full screen 240×320 | **692 ms** |
| 128×128 sprite | 148 ms |
| 64×64 sprite | 37 ms |
| One 5×7 character | 2.05 ms |
| A 20-character label | 41 ms |

**Design rules that follow from this:**

1. **Never redraw the whole screen per frame.** Animate by blitting a sprite into a
   fixed region.
2. **Update meters partially** — redraw only the changed segment of a bar.
3. **Never redraw text every frame.** `DrawChar` calls `FillRect` *per pixel*
   (35 address-window setups per character), so cache labels and update only on change.
4. **The stack is only 2 KB** (`_Min_Stack_Size = 0x800`) and the heap 512 B. Use
   `static` buffers, never large locals — the existing driver already does this.
5. A non-blocking, `HAL_GetTick()`-based scheduler is required so the UI stays
   responsive during animations. **Do not use `HAL_Delay()` in the main loop.**

### Sprite memory budget (RGB565 = 2 bytes/pixel)

| Sprite | Bytes |
|---|---|
| 240×320 (full frame) | 153,600 |
| 128×128 | 32,768 |
| 96×96 | 18,432 |
| **64×64** | **8,192** |

The seven sprites plus the two HUD icons total **59 KB of flash**, well under the
budget, because animation frames are generated by scaling rather than stored.

The built firmware now measures **78,760 bytes of flash and 12,352 bytes of RAM**.
Before `main.c` referenced anything, the same build reported only 12 KB — the
linker was discarding the sprite data because nothing used it.

A full-frame 240×320 RGB565 buffer would be **150 KB of the 320 KB of SRAM**,
which is why the pet is composed into an 8 KB sprite-sized buffer instead.

### Panel colour order

`MADCTL = 0x08` selects **BGR**, and the driver writes the high byte of each RGB565
word first (big-endian on the wire). `ILI9341_DrawBitmap` handles this conversion, so
the converted assets are stored as plain RGB565 and must not be pre-swapped.

The stage background is `#1E2A32` → `0x1946` (`PET_STAGE_COLOR` in `pet_view.h`).
It **must** match the converter's `--stage` value, because the converter snaps every
non-sprite pixel to exactly that colour; otherwise a rectangle shows around the pet.

## 8. AI tools used

Generative AI tools are used in this project. Per the project brief, all AI-assisted
code is tested on real hardware, peripheral and register names are verified against
this project, invented APIs are removed, and the team can explain any subsystem it
submits.

| Tool | Used for |
|---|---|
| AI coding assistant | initial drafts of the logic modules, the host test suites, and the PNG→RGB565 converter |
| AI image generation | the original sprite artwork, later reduced to a limited palette and converted |

A running log with more detail is kept in [`docs/ai-use-log.md`](docs/ai-use-log.md).

### Case study 1: AI suggestion that had to be corrected

**Recommendation rejected:** an early suggestion was to attach a potentiometer to the
ADC and an MPU-6050 accelerometer to **`I2C1` on its default pins `PB6`/`PB7`**.

On checking `Drivers/BSP/GFX01M2/gfx01m2_conf.h` against the pin map, `PB6` is the
GFX01M2's **joystick LEFT** input and `PB7` drives the on-board **LD2** LED. The
default `I2C1` pin assignment is therefore unusable on this board, and the peripheral
plan had to be changed to remap `I2C1` to `PB8`/`PB9`. This is exactly the kind of
invented/unverified detail the brief warns about: the suggestion was plausible in
general but wrong for this specific board, and was only caught by checking the
actual configuration header.

Similarly, an early plan to blink the green **LD1** (`PC7`) for a status indicator was
discarded after the same header showed `PC7` is the **joystick CENTER** input.

### Case study 2: a bug that passed every visual check

**Defect found:** the artwork converter's `rgb565()` was being handed numpy `uint8`
values. Shifting a `uint8` left by 11 **wraps at 8 bits**, so `3 << 11` evaluated to
`0` — meaning **every pixel in every sprite had a zero red field** and a corrupted
green field. The stage colour came out as `0x0046` instead of `0x1946`.

No sprite would have displayed correctly. It survived review because the preview
image was being rendered from the pre-quantization canvas, so the picture being
checked never reflected the bytes being written to disk. Both were fixed: `int()`
in the conversion, and the preview is now decoded back out of the emitted RGB565 so
it shows what the board will actually draw. The corrected output is verified by
checking that every sprite's background is exactly `0x1946` and that the red field
is non-zero.

The lesson worth keeping: **a verification that inspects an intermediate result can
pass while the real output is broken.**

## 9. Repository conventions

- `.gitignore` excludes `build/` (generated artifacts hold absolute paths and must
  never be committed), `mx.scratch`, and macOS `.DS_Store`.
- Commit messages describe the change (e.g. "Implement two-frame feeding animation"),
  not merely that a change happened.
- Every team member commits their own work under their own GitHub account.
- Do not squash or rewrite history before submission — the visible history is
  assessed.
- Do not edit CubeMX-generated files, `syscalls.c`, or the HAL drivers in
  `Drivers/STM32L4xx_HAL_Driver/`. New sources are added to `CMakeLists.txt`
  under `target_sources`, **not** to `cmake/stm32cubemx/CMakeLists.txt`, which
  CubeMX regenerates.
